# tracemine

Read coding agent sessions from Claude Code and Codex into one shape, find every skill invocation, give each one a verdict, and mine failure and fix patterns per skill so that an edit can be proposed against the right `SKILL.md`.

This is an independent prototype. It is not affiliated with, connected to, or reviewed by Nessie. All benchmark data is synthetic and generated by code in this repo.

## The problem

A team that writes skills for its coding agents has no cheap way to know whether a skill is working. The evidence is in the session logs, but the logs are long, each agent writes them in its own format, and a failed tool call inside a skill run does not mean the skill failed. Agents hit an error and recover all the time. I wanted to see how far plain rules can get on three questions:

1. Where in a session was a skill used, in either agent's log format?
2. Did that use go well, and if not, was it the skill's fault?
3. Which failures keep happening under one particular skill and keep being fixed the same way, so the fix belongs in that skill's file?

## Why this matters to Nessie

What I could verify from public pages (links at the bottom):

- The intern posting lists "measuring skill invocations, mining agent traces for failures and repeated workflows, and proposing reviewable edits back to a team's skills" as one area of work, and says cross-provider capture is the hardest unsolved problem in the space.
- Nessie's Skill analytics doc says usage is detected in synced agent sessions, the agent filter is Claude Code or Codex, and success rate is calculated over evaluated invocations.
- Nessie's Skill evals doc lists five results for an invocation: Success, Skill error, Unexpected behavior, Other error, Unknown.
- Nessie's Codex and Claude Code integration docs say it reads session transcripts directly from the machine, including tool use.

So I used those two agents, those five result names, and that definition of success rate. How Nessie actually detects invocations or decides a verdict is not public, and I did not try to guess it. Everything in `skilleval.py` is my own baseline.

The first version of this repo only mined workflows and failure rules from a flat synthetic format, its transcript loader was tested on one hand-written file, and its "skill usage" was a raw error rate over the next 10 calls. That last signal turned out to be a poor proxy (see the results), which is what pushed this version.

## What it does

- `formats.py` parses Claude Code transcript lines and Codex rollout lines into the same event list. Codex shell calls become `Bash`, `apply_patch` becomes `Edit` or `Write` on the file it names, and a shell command that only prints one file becomes `Read`. The same work then produces the same step keys from either agent.
- `skilleval.py` finds skill invocations, cuts out the calls that belong to each one, assigns a verdict with a one-line reason, computes per-skill analytics, and mines failure/fix rules from only the calls inside each skill's invocations.
- `tracemine.py` is the miner from the first version (repeated workflows with a Poisson chance test, failure/fix rules, diff proposals). It now reads through `formats.py`, so it works on mixed logs.
- `bench.py` is the first version's workflow benchmark. `bench_skills.py` is the new verdict benchmark.

## Architecture

```
Claude Code .jsonl ─┐
Codex rollout .jsonl ├─ formats.parse ─ events (user message | tool call with ok/done/error)
flat benchmark .jsonl┘        │
                              ├─ tracemine.mine_workflows / mine_failures   (whole sessions)
                              └─ skilleval.invocations ─ span ─ verdict ─ analytics
                                                          └─ skill_rules ─ tracemine.propose (diff per skill)
```

Six modules and three test files, flat, standard library only.

## Key decisions and tradeoffs

**Failure in Codex has to be read from the output body.** In `codex-rs/protocol/src/models.rs` the function call output payload has a `success` field, but the serializer writes only the body, so the flag is not in the log. I read `metadata.exit_code` when the body is a JSON object, fall back to an `Exit code: N` line, also accept `exit_code` from an `exec_command_end` event, and otherwise treat the call as successful. A failure with none of those markers is missed.

**An invocation is detected from several signals and merged per turn.** A `Skill` tool call, a slash command tag in a user message, a read of `skills/<name>/SKILL.md`, and a `$name` mention of a skill seen elsewhere in the corpus. Codex has no skill tool, and its docs say it reads the full `SKILL.md` when it selects a skill, so the file read is the main Codex signal. Reading another file under the skill folder, listing the skills directory, or `$HOME` in a prompt do not count.

**A span ends at the next user message.** The calls that belong to an invocation run until the next real user message, the next invocation, the end of the session, or 40 calls. This is crude for a skill whose work continues across turns, but it gives the follow-up message a clear role.

**Verdict rules, in order:**

1. The call that loads the skill failed: skill error.
2. The session ends with a call that has no result, or the file ends in a torn line: unknown.
3. A command or file under `skills/<name>/` failed and no later call with the same intent succeeded: skill error.
4. Some other failure was never recovered and it is within the last `tail` calls of the span: other error.
5. The next user message matches a correction pattern ("no, that's not what I asked", "revert that", "you forgot"): unexpected behavior.
6. The span ran less than `min_coverage` of the steps that at least half of this skill's invocations run: unexpected behavior. This profile is learned from the traces themselves without labels, and needs 5 invocations of the skill.
7. Otherwise: success.

Exit status 1 with no output from `grep`, `rg`, `diff`, `test` and similar is not a failure. A failure that is later retried successfully is not held against the invocation, but it does feed the rule miner.

**Rules are attached to a skill only if they are specific to it.** A failure/fix rule goes to a skill when at least 60% of its occurrences across all skills happen under that skill. The stale-edit habit (edit fails, read, edit again) shows up under every skill, so it is reported as general and kept out of every skill's diff.

**No model calls.** The rules are cheap, deterministic and easy to explain, and they clearly fall short on meaning (see held-out results). I would expect a real system to use them as a first pass and send the uncertain cases to a model.

## Install and usage

Python 3.8 or newer. Nothing to install.

```
python demo.py                                  # about 2 seconds
python tracemine.py skills sample_codex_rollout.jsonl sample_session.jsonl
python tracemine.py skills session1.jsonl session2.jsonl --json
python tracemine.py report traces.jsonl --skill SKILL.md
python bench_skills.py                          # about 20 seconds of CPU
python bench.py
```

`skills` takes one file per session, which is how both agents store them. A Codex rollout names its session only on its first line.

## Tests and verified results

`python -m unittest` runs 46 tests: the 17 from the first version unchanged, 10 for the parsers, 19 for invocations, verdicts, analytics and rules. They cover malformed arguments, orphan outputs, unknown line types, torn last lines, calls with no result, sidechain and meta lines, two rollouts in one stream, and a round trip that renders the same session in both formats and checks the parsed calls agree.

### Skill verdicts (`python bench_skills.py`)

The generator plants skill invocations with a known verdict, writes each session as real-shaped Claude Code or Codex lines, and the pipeline has to parse them back. I picked two thresholds (`tail` and `min_coverage`) by grid search on the tune setting only. The held-out setting uses different seeds, four skills that never appear in tune, 60% Codex sessions instead of 30%, twice as many harmless failed probes, up to 3 wrap-up calls after a real failure instead of 1, and follow-up messages that I wrote after the correction patterns and did not adjust the patterns for.

| setting | sessions | tool calls | invocations | found | accuracy | macro F1 |
|---|---|---|---|---|---|---|
| tune (3 seeds) | 900 | 27,067 | 1,670 | 1,670 | 0.969 | 0.971 |
| held-out (2 seeds) | 600 | 18,380 | 1,097 | 1,097 | 0.774 | 0.810 |

Held-out per verdict:

| verdict | n | precision | recall | F1 |
|---|---|---|---|---|
| success | 516 | 0.742 | 0.864 | 0.799 |
| skill_error | 106 | 1.000 | 1.000 | 1.000 |
| unexpected_behavior | 231 | 0.725 | 0.649 | 0.685 |
| other_error | 184 | 0.707 | 0.473 | 0.567 |
| unknown | 60 | 1.000 | 1.000 | 1.000 |

How I read this:

- The drop from 0.969 to 0.774 is the honest number. On held-out, 74 of 184 real failures were called success because the agent ran a few more calls after giving up and the failure fell outside the two-call tail, and 81 of 231 unexpected cases were called success because the user's complaint did not match any pattern ("that broke staging, roll it back").
- skill_error and unknown score 1.000 in both settings. That says my generator makes those two cases mechanically easy (a failing path under the skill folder, a call with no result). It does not say the problem is solved.
- No planted invocation was missed and no decoy was counted, in either format. The generator only plants invocations the detector has a signal for, so this checks the parsers and the merging more than it checks detection in the wild.
- As a two-way call (success or not, unknown left out), the rules got 812 of 1,037 right on held-out (0.783). The first version's signal, any failed call in the 10 calls after the invocation, got 570 of 1,037 (0.550).
- Per-skill rules: one failure habit is planted under one skill per setting. It was attached to the right skill in all 5 runs (3 tune, 2 held-out) and nothing was attached to a wrong skill.

### Workflow mining (`python bench.py`, unchanged from the first version)

5 seeds of 400 sessions, 73,468 calls. The chance test reports 34 workflows of which 30 are the planted ones (support-only baseline reports 666), and 25 of 25 planted failure rules are recovered with no wrong rule. Those thresholds were tuned on the same generator, so treat them as a sanity check.

Both benchmark scripts also write their numbers to `bench_results.json`, which is generated and not checked in.

## Limitations and next steps

- I have not run this on a real exported session from either agent. The Codex payload field names come from the public Rust source. The outer rollout line shape (`timestamp`, `type`, `payload`), the shell argument shapes, the `Exit code:` text form, and the Claude Code transcript details (`isSidechain`, `isMeta`, the slash command tag) come from my own reading and use of those tools, and I could not verify them against a spec. Field drift between agent versions is likely.
- Verdicts are rules. They do not understand what the skill was supposed to do. The held-out confusion matrix shows where that breaks.
- "Unknown" in Nessie's doc means the evaluation is still running. I reuse the name for a session that was cut off, which is a different thing.
- The step profile is learned from the same traces it judges, so a skill that is usually misused would get a misleading profile.
- Only two agents. Cursor, OpenCode and the others Nessie lists each need their own parser.
- A span ends at the next user message, so multi-turn skill runs are split.
- Proposed edits are appended lines. They do not rewrite or check existing instructions.
- Next: test against real sessions of my own, make the tail rule depend on whether later calls are related to the failed one, and add an optional second pass that sends only the low-confidence spans to a model.
